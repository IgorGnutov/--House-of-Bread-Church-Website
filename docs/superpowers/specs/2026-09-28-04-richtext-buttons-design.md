# Спека 4. Форматований текст і редаговані посилання кнопок

**Дата:** 2026-09-28, **переглянуто 2026-11-16** (див. «Що змінилося 2026-11-16»).
**Порядок:** після Етапу 5 (Storyblok як джерело правди) і Спеки 5 (стрічка Facebook). Не залежить від домену
й Етапу 6, але інструкція редактора (Етап 6) має описати нові поля.

## Мета

Дати редактору в Storyblok дві речі, яких зараз немає:

1. **Форматування текстів з описом** — повноцінний richtext: усе, що вміє редактор Storyblok, крім
   кольорів, виділення кольором, вирівнювання й вставних блоків. Зараз усі тексти прості, абзаци
   розділені порожнім рядком, розмітка заборонена схемою (крім `homepage.hero.title`).
2. **Адресу кожної кнопки.** Зараз редагується лише `projects.ctaUrl`. Решта адрес або прописані в
   шаблонах (`#contacts`, `#media`, `/testimonies/`, `m.me/…`, `mailto:leaders@…`), або виводяться з
   налаштувань чи даних.

Дизайн не змінюється: на поточному контенті сайт виглядає піксель у піксель так само.

сторінку з палітри токенів; для вставних блоків спершу треба спроєктувати самі блоки.

## Рішення

### Бібліотека

Рендер — `@storyblok/richtext@^5.5.2` (рекомендація замовника). Спайк 2026-09-28 (5.3.2):

- у бандлі лише `renderRichText`, ~9 kB. tiptap і happy-dom тягнуть лише підшляхи
  `html-parser` / `markdown-parser`, які ми не імпортуємо. Прев'ю-воркер лишається легким;
- текст екранується (`<script>` → `&lt;script&gt;`);
- `renderers` перевизначають вузли й марки. У свій рендерер `attrs.href` приходить **не
  екранованим**, тож екрануємо самі;
- `javascript:` у `href` бібліотека пропускає, невідомий вузол мовчки рендерить його дітей.
  **Тому межа безпеки — zod-схема, а не бібліотека.**

Ці висновки перевіряються тестом на 5.5.2 до того, як на них спирається решта (типи 5.5.2 уже звірено:
назви вузлів і марок нижче — з них).

### Два рівні форматування

| Рівень | Дозволено | Поля |
|---|---|---|
| **`rich`** (блоковий) | усе з інлайн-рівня, а ще: заголовки `h2`–`h6` (`h1` — заголовок сторінки), маркований і нумерований список (з вкладеними), цитата, горизонтальна лінія, блок коду, таблиця, картинка, емодзі | `ministries.body`, `churches.body`, `projects.body`, `pages.*.body`, `pastors.bio`, `testimonies.text` (text-варіант) |
| **`richCard`** | як `richInline`, але без посилань і якорів | `ministries.summary`, `churches.lead`, `projects.lead`, `leader-resources.description` — вони стоять усередині `<a class="min-card">`, `church-card`, `project-card`, `doc-card` / `res-card` |
| **`richInline`** | абзаци, перенос рядка; марки: жирний, курсив, підкреслення, закреслення, верхній і нижній індекс, код, посилання, якір; емодзі | `pages.*.lead`, `pages.*.sections.past_lead` / `elders_lead`, `pages.*.help.desc`, `homepage.hero.vision`, `homepage.about.lead`, `homepage.beliefs[]`, `homepage.news.lead`, `homepage.news.items[].text`, `homepage.wwb.items[].text`, `homepage.testimonies.items[].text`, `homepage.ministries.lead`, `homepage.pastors.lead`, `homepage.donate.quote` / `thanks`, `homepage.footer.about` |
| простий текст (як зараз) | — | заголовки, підписи, кнопки, меню, `alt`, `seo.*`, `hero.title` (лишається `localizedHtml`) |

Інлайн-поля стоять у шаблоні всередині `<p>` або `<h2>`, а часто й у картках фіксованої висоти.
Списки, заголовки, таблиці й картинки там зламали б і розмітку (`<p>` у `<p>`), і вигляд. Тому
`richInline` і `richCard` рендеряться без обгорток абзаців: абзаци склеюються через `<br>`. Поле `richCard`
на детальній сторінці (напр. `ministries.summary` як підзаголовок) теж без посилань: одне поле — одна панель.

### Формат даних

Документ Storyblok (ProseMirror) зберігається як є, у парі мов:

```json
"body": {
  "uk": { "type": "doc", "content": [ { "type": "paragraph", "content": [ { "type": "text", "text": "…" } ] } ] },
  "en": { "type": "doc", "content": [ … ] }
}
```

Відкинуті варіанти: Markdown (не вміє підкреслення, індексів і частини іншого; редактор бачить `**…**`
замість WYSIWYG) і HTML у файлах, згенерований на `cms:pull` (два конвертори й санітайзер, найменш точне
перетворення туди й назад, а посилання на сторінки не «запекти»: адреса залежить від мови й збірки).

### Схема (`richDoc('rich' | 'inline' | 'card')` у `src/lib/schema.mjs`)

Суворий allowlist: один обхід документа в `superRefine`, який на кожне порушення додає помилку з
точним шляхом (`body.uk.content.0.content.2.marks.0.attrs.href`) і поясненням. Рекурсивні
`z.object` на невідомому вузлі дали б лише «Invalid input» по кожній гілці union.

Вузли (назви — з типів `@storyblok/richtext` 5.5.2):

- `doc` → блоки;
- інлайн-рівень: `paragraph` → `text`, `hard_break`, `emoji`;
- блоковий рівень, додатково: `heading` (`attrs.level` ∈ 2…6), `bullet_list`, `ordered_list`
  (`attrs.order` — ціле ≥ 1, необовʼязкове), `list_item` (усередині — блоки, крім `heading`),
  `blockquote` (усередині — блоки), `horizontal_rule`, `code_block` (лише `text`, без марок; `attrs.class`
  — `language-…` або null), `table` → `tableRow` → `tableHeader` / `tableCell` (усередині — абзаци;
  `colspan`/`rowspan` — цілі ≥ 1), `image`;
- `image.attrs` після нормалізації — рівно `src`, `alt`, `title` (необовʼязковий). `src` — `http(s)://…`
  або `uploads/…` (файл медіатеки після `cms:pull`). `alt` — непорожній, як у галереї (Спека 1):
  повідомлення підказує заповнити опис картинки в медіатеці Storyblok;
- `emoji.attrs` — `emoji` (непорожній рядок; рендериться символом, `fallbackImage` не зберігається).

Марки на `text`: `bold`, `italic`, `underline`, `strike`, `superscript`, `subscript`, `code`, `link`,
`anchor`.

- `link.attrs` після нормалізації — рівно `href` і `linktype` ∈ `url` / `email` / `asset`; вкладку вибирає
  рендер за адресою, тож `target` у даних не зберігається. `linktype: story` у файлах не буває: його
  розвʼязує `fromStory` (нижче);
- `anchor.attrs.id` — `[a-z0-9-]+` (стане `id` елемента; на сторінку посилаються як `#id`);
- зайве поле в будь-якому вузлі чи марці — помилка;
- `text.text` — непорожній рядок;
- документ має містити непорожній текст або картинку. Порожній документ для обовʼязкового поля — та сама
  помилка, що й для порожнього рядка зараз. Обидві мови обовʼязкові;
- повідомлення називають, що саме не так: «колір/виділення/вирівнювання не підтримуються — дизайн
  використовує лише свої кольори», «вставні блоки в тексті не підтримуються», «списки, заголовки,
  таблиці й картинки дозволені лише в основному тексті», «посилання: …».

Посилання в richtext і всі адреси кнопок проходять один валідатор **`linkUrl`**:
`https://…`, `http://…`, `mailto:…`, `tel:…`, `/…` (внутрішній шлях, не `//…`), `uploads/…` (файл сайту) і
`#якір` (≥ 1 символ після `#`). Відхиляються `javascript:`, голий `#` і все інше. `uploads/…` потрібен,
бо `cms:pull` переписує **будь-який** рядок з адресою файлу медіатеки Storyblok на відносний
`uploads/cms/…` — уже після перевірок. Без нього посилання на PDF з медіатеки пройшло б `cms:pull` і
завалило б збірку. Існування файлу перевіряє `findBrokenLinks`. Для `linktype: email` Storyblok кладе в
`href` голу адресу — нормалізація (нижче) додає `mailto:`.

### Посилання на сторінки сайту (`linktype: story`)

Storyblok кешує `href` посилання на історію й не оновлює його, коли історію перейменовують. Тому адреса
береться не з `href`, а з `uuid`:

- `storiesToEntries` (і `cms:pull`, і прев'ю, і `cms:import`/`verify`) уже має всі історії простору. З них
  будується карта `uuid → шлях сайту` і передається в `fromStory`;
- шлях — без мови й `base`, як `localePath` його приймає: `ministries/<slug>`, `churches/<slug>`,
  `projects/<slug>` → детальна сторінка; `pages/<id>` → маршрут сторінки (`/about/` тощо);
  `settings/homepage` → `/`; історія свідчення, пастора чи ресурсу → сторінка відповідного списку
  (`/testimonies/`, `/pastors/`, `/leaders/`); інші одиночки сторінки не мають — помилка
  «ця історія не має сторінки на сайті»;
- `attrs.anchor` (якір, вибраний у редакторі) додається як `#…`;
- невідомий `uuid` — посилання знімається, текст лишається, у журнал іде попередження з назвою поля й
  текстом посилання. `cms:pull` бачить лише опубліковані історії: редактор, який опублікував сторінку A з
  посиланням на ще не опубліковану B, не повинен блокувати весь деплой. Публікація B запускає новий
  деплой (вебхук), і посилання зʼявляється саме. Прев'ю бачить чернетку B і показує посилання одразу.
  Видалена історія поводиться так само;
- результат нормалізується в `{ href: '/ministries/youth/', linktype: 'url' }` — у файлах це звичайне
  внутрішнє посилання. Кожен `cms:pull` розвʼязує `uuid` заново, тож у файлах завжди поточний slug.
  Наслідок: імпорт **з файлів** запише в Storyblok посилання вже як «URL», а не «Story». Це стається лише
  з історією, дані якої в файлах відрізняються від Storyblok (міграція чи сід), і на сайті нічого не
  змінює. Якщо дані вже рівні, а застарів лише відбиток (історію правили в Storyblok, потім `cms:pull`),
  імпорт не переписує історію з файлів, а лишає її вміст і оновлює тільки `import_hash` — інакше
  `linktype: 'story'` і метадані картинок редактора пропали б;
- посилання на сторінку, яка не будується (`about` без `body`), потрапляє в HTML і валить
  `findBrokenLinks` — як і будь-яке інше бите посилання.

### Модель і конвертація Storyblok

- Нові типи пар у `model.mjs`: `rich(label)` / `richInline(label)` →
  `{ kind: 'pair', item: 'richtext', level }`. У Storyblok — два поля `richtext` (`<key>_uk`,
  `<key>_en`) з `customize_toolbar: true` і панеллю рівно з дозволених кнопок (`TOOLBAR[level]`). Точні
  ключі кнопок Storyblok звіряються з документацією й живою формою (задача з живим простором);
  розбіжність — зміна `TOOLBAR`, не схеми. Кнопки кольору, виділення, вирівнювання, стилів і блоків до
  панелі не входять; якщо редактор усе ж уставить таке (вставка з Word), схема назве поле.
- `checkModel` упізнає `localizedRich` / `localizedRichInline` за тотожністю, як `localized`, і
  звіряє рівень.
- `fromStory` **нормалізує** документ: лишає тільки атрибути з allowlist (редактор Storyblok
  дописує, наприклад, `textAlign: null`, а в посиланні — `uuid`, `target`, `custom`; у картинці — `id`,
  `copyright`, `source`, `meta_data`), розвʼязує посилання на історії, обрізає порожні абзаци на початку
  й у кінці, додає `mailto:` до email-посилань. Порожні значення атрибутів, які Storyblok пише завжди
  (`textAlign: null`, `class: null`), відкидаються; **непорожні** заборонені (вирівнювання по центру) —
  лишаються, щоб схема назвала їх, а не сторінка мовчки втратила задумане. Так само невідомі вузли й
  марки лишаються як є. Порожній документ (`''`, `null` або самі порожні абзаци) = «поля немає»: для
  nullable-полів `null`, для обовʼязкових — порожнє значення, яке відкине схема.
- **Рядок** у полі richtext (історія, збережена ще зі старою моделлю textarea) читається тим самим
  `docFromText`, що й міграція файлів. Імпорт порівнює *дані* історії (`fingerprint(fromStory(…))`), а не
  сирий JSON, тож після міграції файлів дані збігаються — імпорт лише оновлює історії, без `--force`. А
  `cms:pull` у CI працює і до імпорту: злиття гілки не блокує деплой.
- `toStory` пише документ без змін, а картинки з `uploads/…` — як asset медіатеки (`src` — адреса
  Storyblok, `id` — asset): ті самі `asset()` і завантаження, що в полях-картинках (`scripts/cms/sync.mjs`
  збирає й картинки з richtext). Нормалізація ідемпотентна, тому перетворення файли → Storyblok → файли
  точне, а `cms:verify`, `import_hash` і захист від перезапису працюють як раніше.
- `cms:pull`: картинки й посилання на файли медіатеки в тексті локалізує наявний `localizeAssets` (він
  обходить усі рядки даних). Тест із такою картинкою.

### Рендер

- `src/lib/richtext.mjs` — дані без рендеру (`isDoc`, `docFromText`, `normalizeDoc`, `richPlain`):
  їх читають схема, конвертація і прев'ю-воркер. `richPlain(doc)` — простий текст (блоки через `\n\n`,
  `hard_break` → пробіл; картинки, лінії й код пропускаються) для SEO-фолбеків (`resolveMeta`,
  `pageDescription`) і JSON-LD.
- `src/lib/richtext-render.mjs` — `renderRich(doc, { base, lang, inline })`: `renderRichText` з
  перевизначеними рендерерами:
  - `link`: `linkHref(base, lang, href)`, атрибути екрануються, зовнішнє посилання (`http(s)://`)
    отримує `target="_blank" rel="noopener noreferrer"`;
  - `paragraph`: порожній не рендериться; в `inline` абзаци склеюються через `<br>`;
  - `image`: `<img src={assetUrl(base, src)} alt title loading="lazy" decoding="async">`;
  - `table`: обгортка з горизонтальною прокруткою, щоб широка таблиця не розпирала сторінку на телефоні;
  - `anchor`: `<span id>`; `emoji`: сам символ;
  - решта вузлів — HTML бібліотеки з класами `rt-*` (`rt-h`, `rt-list`, `rt-link`, `rt-quote`, `rt-code`,
    `rt-table`, `rt-img`, `rt-hr`). Стилі — один раз у `base.css`, на наявних токенах; посилання
    кольором навколишнього тексту, картинки й таблиці не ширші за колонку.
  Апостроф — `&#39;`, як в Astro: тоді перехід на richtext доводиться побайтовим порівнянням збірок.
- `src/components/Rich.astro` — `<Rich value={pair} lang={lang} inline />`: `pickRich` → `renderRich` →
  `<Fragment set:html>`. **Єдине місце, де richtext потрапляє в `set:html`** (тест).
- `linkHref()` у `paths.mjs` приймає весь `linkUrl`: `mailto:`, `tel:`, `#…` повертаються як є,
  `/…` локалізується, `uploads/…` — під `base`, решта — помилка. `linkAttrs()` додає `target`/`rel`
  зовнішнім адресам.

### Шаблони

- Інлайн-поле: `<p>{pick(x, lang)}</p>` → `<p><Rich value={x} lang={lang} inline /></p>`.
  Розмітка й вигляд не змінюються.
- Блокове поле без обгортки там, де стилі сторінки задані предком (`.info p` у church/project,
  `.pastor-body p`, `.elder-card p`, `.prose p`): абзаци стають на місце старого `<p>`, один абзац дає
  той самий HTML. Обгортка `<div>` — лише для `ministries.body` (`.desc`: стиль на класі самого `<p>`) і
  `testimonies.text` (`.tst-text`: `p{flex:1}` на кожному абзаці ділив би вільне місце картки). Стилі
  обгорток — у стилях сторінки, на наявних токенах, без `<style>` в `.astro`.
- `about` / `contacts` / `donate`: `.prose` рендерить `Rich` замість `paragraphs()`.
  `paragraphs()` видаляється, коли стає непотрібним.

### Кнопки

**Вкладка — за типом адреси:** `http(s)://` відкривається в новій вкладці з `noopener noreferrer`,
решта — в тій самій. Дві зміни поведінки: «Дивитися» в першому екрані відкриватиме YouTube у новій
вкладці, як уже робить «Трансляція» в шапці, а «Прокласти маршрут» на сторінці церкви — Google Maps у
новій вкладці, як уже робить кнопка карти на сторінці контактів.

**Усі поля необовʼязкові** (`linkUrl.nullable()`): порожньо — кнопка веде туди ж, куди зараз. Опис поля
у формі Storyblok називає цей фолбек. Наявні історії цих ключів не мають — `fromStory` читає їх як `null`,
тож злиття гілки не ламає `cms:pull`, а імпорт не бачить конфлікту.

| Поле | Кнопка | Порожньо — веде на |
|---|---|---|
| `homepage.hero.contactsUrl` | «Контакти» в першому екрані | `#contacts` |
| `homepage.news.items[].url` | «Більше» — своє в кожної новини (ручні картки; видно, лише коли постів Facebook нуль) | `#media` |
| `homepage.testimonies.allUrl` | «Усі свідчення» | `/testimonies/` |

| `pages.*.help.btnUrl` | «Потрібна допомога» | pastors — `https://m.me/dom.hleba.org`, leaders — `mailto:leaders@houseofbread.church` (константи лишаються в коді як фолбек) |
| `homepage.cta.liveUrl` | «Трансляція» (шапка й мобільне меню) | `site-settings.social.youtube` + `/streams` |
| `homepage.hero.watchUrl` | «Дивитися» | те саме |
| `homepage.hero.donateUrl` | «Пожертвувати» в першому екрані | `donate-settings.liqpayUrl` |

## Міграція

1. `npm run cms:pull` — правки редактора потрапляють у файли.
2. Одноразовий скрипт `scripts/migrate-richtext.mjs` переписує `src/content`: рядок довгого поля →
   документ (межа абзаців — порожній рядок, одиночний `\n` → `hard_break`); нові поля кнопок → `null`. Поля переходять на richtext у кількох задачах плану, тож скрипт
   ідемпотентний і видаляється в останній задачі.
3. **Лише з окремого дозволу**: `cms:pull` → `cms:import` (dry-run: оновлення компонентів і `update`
   кожної історії з форматованими полями, без конфліктів) → `cms:import -- --apply` → повторний dry-run
   (`0 змін`) → `cms:verify`. `--force` не потрібен (див. «Модель і конвертація»). Злиття гілки може
   бути і до цього кроку: до імпорту `cms:pull` читає рядки старої моделі як документи.

## Пробний документ редактора

Нормалізацію треба перевірити на документі, який набрала людина в редакторі Storyblok: атрибути, які той
дописує, через API не підробиш. Справжні поля до злиття на richtext не перемикаються: код на `main` не вміє
їх читати, і деплой зламався б. Тому (погоджено з власником 2026-11-16):

1. Management-токеном у просторі створюються тимчасовий компонент `richtext_probe` (поля всіх трьох
   рівнів, панелі — з `TOOLBAR`) і історія в папці `_probe`. Сайт її пропускає (`storiesToEntries`:
   «поза папками сайту — пропущено»), тож на деплой вона не впливає.
2. Власник заповнює її в Storyblok за списком: кожна кнопка панелі хоча б раз, картинка з медіатеки (з
   `alt` і без), посилання на сторінку (з якорем), на файл медіатеки, на пошту, вставка з Word (з кольором і
   вирівнюванням — їх має відкинути схема).
3. JSON історії (Delivery API, `draft`) лягає фікстурою в `tests/fixtures/`; на ній тестуються
   нормалізація, схема й рендер. Заодно звіряються ключі кнопок `TOOLBAR` з тим, що показала форма.
4. Компонент і історія видаляються.

## Ризики

| Ризик | Що робимо |
|---|---|
| Редактор Storyblok дописує атрибути, яких немає в allowlist | нормалізація у `fromStory`; фікстура з пробного документа редактора (розділ «Пробний документ редактора») — з кожним вузлом і маркою всіх рівнів |
| Зміна типу поля textarea → richtext на існуючих історіях | `fromStory` читає рядок як документ; імпорт без `--force` оновлює історії; повторний dry-run показує `0 змін` |
| Посилання на файл медіатеки Storyblok у тексті | `uploads/…` у `linkUrl`; тест `cms:pull` з таким посиланням |
| Картинка в тексті без `alt` у медіатеці | схема відкидає з підказкою, де заповнити; `cms:pull` нічого не записує, прев'ю показує сторінку проблем |
| Посилання на історію, яку перейменували чи видалили | адреса з поточного slug за `uuid`; видалена — помилка з назвою поля |
| Широка таблиця чи картинка на телефоні | таблиця в обгортці з прокруткою, `max-width:100%` для картинок; e2e-скріншот проби на ширині телефона |
| Якір у тексті збігається з `id` сторінки (`contacts`) або з іншим якорем | перевірка дублікатів `id` на сторінці в `site.test.js` |
| Блоковий текст зсуває вигляд детальних сторінок | скріншоти всіх сторінок до/після на поточному контенті, побайтове порівняння PNG |
| Посилання з richtext на неіснуючу сторінку | потрапляє в HTML → `findBrokenLinks` валить `npm test` |
| Битий якір (`#contacts` → id немає) | нова перевірка якорів у `site.test.js` |

## Критерії готовності

1. Усі поля з таблиці рівнів — richtext у Storyblok з панеллю свого рівня; прості поля не змінилися.
2. Схема відкидає все поза allowlist із зрозумілим повідомленням; `npm test` зелений.
3. На поточному контенті статичний вихід відрізняється від вихідного лише очікуваним (див. план),
   e2e-скріншоти збігаються.
4. Пробна збірка з **кожним** дозволеним вузлом і маркою в кожному полі (обидва рівні) збирається,
   розмітка валідна, битих посилань і дублікатів `id` немає; на ширині телефона немає горизонтальної
   прокрутки сторінки.
5. Посилання на історію веде на поточну адресу сторінки в обох мовах; після перейменування історії й
   `cms:pull` — на нову.
6. Кожна кнопка з таблиць веде на адресу зі свого поля; порожні необовʼязкові — на фолбек.
7. Файли → Storyblok → файли — без різниці (`cms:verify` на фейку, з картинкою в тексті; на живому
   просторі — після імпорту).
8. CLAUDE.md описує richtext, рівні, `linkUrl`, посилання на історії й `Rich.astro`.
