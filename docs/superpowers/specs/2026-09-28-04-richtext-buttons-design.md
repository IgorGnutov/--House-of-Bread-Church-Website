# Спека 4. Форматований текст і редаговані посилання кнопок

**Дата:** 2026-09-28
**Порядок:** після Етапу 5 (Storyblok як джерело правди). Не залежить від домену й Етапу 6, але
інструкція редактора (Етап 6) має описати нові поля.

## Мета

Дати редактору в Storyblok дві речі, яких зараз немає:

1. **Форматування довгих текстів** — жирний, курсив, посилання, а в основних текстах ще списки й
   підзаголовки. Зараз усі тексти прості, абзаци розділені порожнім рядком, розмітка заборонена
   схемою (крім `homepage.hero.title`).
2. **Адресу кожної кнопки.** Зараз редагується лише `projects.ctaUrl`. Решта адрес або прописані в
   шаблонах (`#contacts`, `#media`, `/testimonies/`, `m.me/…`, `mailto:leaders@…`), або виводяться з
   налаштувань чи даних.

Дизайн не змінюється: на поточному контенті сайт виглядає піксель у піксель так само.

## Рішення

### Бібліотека

Рендер — `@storyblok/richtext@^5.3` (рекомендація замовника). Спайк 2026-09-28 (5.3.2):

- у бандлі лише `renderRichText`, ~9 kB. tiptap і happy-dom тягнуть лише підшляхи
  `html-parser` / `markdown-parser`, які ми не імпортуємо. Прев'ю-воркер лишається легким;
- текст екранується (`<script>` → `&lt;script&gt;`);
- `renderers` перевизначають вузли й марки. У свій рендерер `attrs.href` приходить **не
  екранованим**, тож екрануємо самі;
- `javascript:` у `href` бібліотека пропускає, невідомий вузол мовчки рендерить його дітей.
  **Тому межа безпеки — zod-схема, а не бібліотека.**

### Два рівні форматування

| Рівень | Дозволено | Поля |
|---|---|---|
| **`rich`** (блоковий) | абзаци, `h3`, маркований і нумерований список, перенос рядка, жирний, курсив, посилання | `ministries.body`, `churches.body`, `projects.body`, `pages.*.body`, `pastors.bio`, `testimonies.text` (text-варіант) |
| **`richInline`** | абзаци, перенос рядка, жирний, курсив, посилання | `ministries.summary`, `churches.lead`, `projects.lead`, `leader-resources.description`, `pages.*.lead`, `pages.*.sections.past_lead` / `elders_lead`, `pages.*.help.desc`, `homepage.hero.vision`, `homepage.about.lead`, `homepage.beliefs[]`, `homepage.news.lead`, `homepage.news.items[].text`, `homepage.fb.text`, `homepage.wwb.items[].text`, `homepage.testimonies.items[].text`, `homepage.ministries.lead`, `homepage.pastors.lead`, `homepage.donate.quote` / `thanks`, `homepage.footer.about` |
| простий текст (як зараз) | — | заголовки, підписи, кнопки, меню, `alt`, `seo.*`, `hero.title` (лишається `localizedHtml`) |

Інлайн-поля стоять у шаблоні всередині `<p>` або `<h2>`, а часто й у картках фіксованої висоти.
Списки й заголовки там зламали б і розмітку (`<p>` у `<p>`), і вигляд. Тому `richInline` рендериться
без обгорток абзаців: абзаци склеюються через `<br>`.

### Формат даних

Документ Storyblok (ProseMirror) зберігається як є, у парі мов:

```json
"body": {
  "uk": { "type": "doc", "content": [ { "type": "paragraph", "content": [ { "type": "text", "text": "…" } ] } ] },
  "en": { "type": "doc", "content": [ … ] }
}
```

Відкинуті варіанти: Markdown (редактор бачить `**…**` замість WYSIWYG, крихкі крайові випадки з
`*`/`_` у тексті) і санітизований HTML (два конвертори й санітайзер, найменш точне перетворення туди й назад).

### Схема (`richDoc('block' | 'inline')` у `src/lib/schema.mjs`)

Суворий allowlist: один обхід документа в `superRefine`, який на кожне порушення додає помилку з
точним шляхом (`body.uk.content.0.content.2.marks.0.attrs.href`) і поясненням. Рекурсивні
`z.object` на невідомому вузлі дали б лише «Invalid input» по кожній гілці union.

- вузли: `doc` → блоки. `block`: `paragraph`, `heading` (`attrs.level` = 3), `bullet_list`, `ordered_list`
  (`attrs.order` — ціле ≥ 1, необовʼязкове), `list_item` (усередині — `paragraph` або вкладений список).
  `inline`: лише `paragraph`. У блоках: `text`, `hard_break`;
- марки на `text`: `bold`, `italic`, `link` (`attrs` — рівно `href` і `linktype` ∈ `url` / `email` /
  `asset`; вкладку вибирає рендер за адресою, тож `target` у даних не зберігається);
- зайве поле в будь-якому вузлі чи марці — помилка;
- `text.text` — непорожній рядок;
- документ має містити непорожній текст. Порожній документ для обовʼязкового поля — та сама помилка,
  що й для порожнього рядка зараз. Обидві мови обовʼязкові;
- повідомлення називають, що саме не так: «таблиці/картинки/блоки в цьому полі не підтримуються»,
  «списки й підзаголовки дозволені лише в основному тексті», «посилання: …».

Посилання в richtext і всі адреси кнопок проходять один валідатор **`linkUrl`**:
`https://…`, `http://…`, `mailto:…`, `tel:…`, `/…` (внутрішній шлях, не `//…`), `uploads/…` (файл сайту) і
`#якір` (≥ 1 символ після `#`). Відхиляються `javascript:`, голий `#` і все інше. `uploads/…` потрібен,
бо `cms:pull` переписує **будь-який** рядок з адресою файлу медіатеки Storyblok на відносний
`uploads/cms/…` — уже після перевірок. Без нього посилання на PDF з медіатеки пройшло б `cms:pull` і
завалило б збірку. Існування файлу перевіряє `findBrokenLinks`. Для посилань у richtext ще й
**`linktype: story` відхиляється** з підказкою «вкажіть адресу вручну, напр. /ministries/youth/»:
Storyblok кешує `href` посилань на історії й не оновлює його, коли історію перейменовують. Для
`linktype: email` Storyblok кладе в `href` голу адресу — нормалізація (нижче) додає `mailto:`.

### Модель і конвертація Storyblok

- Нові типи пар у `model.mjs`: `rich(label)` / `richInline(label)` →
  `{ kind: 'pair', item: 'richtext', level }`. У Storyblok — два поля `richtext` (`<key>_uk`,
  `<key>_en`) з `customize_toolbar: true` і панеллю рівно з дозволених кнопок: `block` —
  `bold, italic, link, paragraph, h3, list, olist`; `inline` — `bold, italic, link`.
- `checkModel` упізнає `localizedRich` / `localizedRichInline` за тотожністю, як `localized`, і
  звіряє рівень.
- `fromStory` **нормалізує** документ: лишає тільки атрибути з allowlist (редактор Storyblok
  дописує, наприклад, `textAlign: null`, а в посиланні — `uuid`, `target`, `custom`), обрізає
  порожні абзаци на початку й у кінці, додає `mailto:` до email-посилань. Невідомі вузли й марки
  **не** викидаються, а лишаються як є: схема назве їх, а не сторінка мовчки втратить текст.
  Порожній документ (`''`, `null` або самі порожні абзаци) = «поля немає»: для nullable-полів `null`,
  для обовʼязкових — порожнє значення, яке відкине схема.
- **Рядок** у полі richtext (історія, збережена ще зі старою моделлю textarea) читається тим самим
  `docFromText`, що й міграція файлів. Імпорт порівнює *дані* історії (`fingerprint(fromStory(…))`), а не
  сирий JSON, тож після міграції файлів дані збігаються — імпорт лише оновлює історії, без `--force`. А
  `cms:pull` у CI працює і до імпорту: злиття гілки не блокує деплой.
- `toStory` пише документ без змін (він уже нормалізований). Нормалізація ідемпотентна, тому
  перетворення файли → Storyblok → файли точне, а `cms:verify`, `import_hash` і захист від перезапису
  працюють як раніше.

### Рендер

- `src/lib/richtext.mjs` — дані без рендеру (`isDoc`, `docFromText`, `normalizeDoc`, `richPlain`):
  їх читають схема, конвертація і прев'ю-воркер. `richPlain(doc)` — простий текст (блоки через `\n\n`,
  `hard_break` → пробіл) для SEO-фолбеків (`resolveMeta`, `pageDescription`) і JSON-LD.
- `src/lib/richtext-render.mjs` — `renderRich(doc, { base, lang, inline })`: `renderRichText` з
  перевизначеними `link`, `paragraph`, `heading`, `bullet_list`, `ordered_list`. `link`:
  `linkHref(base, lang, href)`, атрибути екрануються, зовнішнє посилання (`http(s)://`) отримує
  `target="_blank" rel="noopener noreferrer"`. `paragraph`: порожній не рендериться; в `inline` абзаци
  склеюються через `<br>`. Списки, `h3` і посилання отримують класи `rt-list`, `rt-h`, `rt-link` — їхні
  стилі один раз у `base.css`, посилання кольором навколишнього тексту. Апостроф — `&#39;`, як в Astro:
  тоді перехід на richtext доводиться побайтовим порівнянням збірок.
- `src/components/Rich.astro` — `<Rich value={pair} lang={lang} inline />`: `pickRich` → `renderRich` →
  `<Fragment set:html>`. **Єдине місце, де richtext потрапляє в `set:html`** (тест).
- `linkHref()` у `paths.mjs` приймає весь `linkUrl`: `mailto:`, `tel:`, `#…` повертаються як є,
  `/…` локалізується, `uploads/…` — під `base`, решта — помилка. `linkAttrs()` додає `target`/`rel`
  зовнішнім адресам.

### Шаблони

- Інлайн-поле: `<p>{pick(x, lang)}</p>` → `<p><Rich value={x} lang={lang} inline /></p>`.
  Розмітка й вигляд не змінюються.
- Блокове поле без обгортки там, де стилі сторінки задані предком (`.info p` у church/project,
  `.pastor-body p`, `.elder-card p`, `.prose p`): абзаци стають на місце старого `<p>`, один абзац дає
  той самий HTML. Обгортка `<div>` — лише для `ministries.body` (`.desc`: стиль на класі самого `<p>`) і
  `testimonies.text` (`.tst-text`: `p{flex:1}` на кожному абзаці ділив би вільне місце картки). Стилі
  обгорток — у стилях сторінки, на наявних токенах, без `<style>` в `.astro`.
- `about` / `contacts` / `donate`: `.prose` рендерить `Rich` замість `paragraphs()`.
  `paragraphs()` видаляється, коли стає непотрібним.

### Кнопки

**Вкладка — за типом адреси:** `http(s)://` відкривається в новій вкладці з `noopener noreferrer`,
решта — в тій самій. Дві зміни поведінки: «Дивитися» в першому екрані відкриватиме YouTube у новій
вкладці, як уже робить «Трансляція» в шапці, а «Прокласти маршрут» на сторінці церкви — Google Maps у
новій вкладці, як уже робить кнопка карти на сторінці контактів.

**Обовʼязкові поля, заповнені поточними адресами:**

## Міграція

1. `npm run cms:pull` — правки редактора потрапляють у файли.
2. Одноразовий скрипт `scripts/migrate-richtext.mjs` переписує `src/content`: рядок довгого поля →
   документ (межа абзаців — порожній рядок, одиночний `\n` → `hard_break`); нові поля кнопок →
   поточні адреси або `null`. Поля переходять на richtext у кількох задачах плану, тож скрипт
   ідемпотентний і видаляється в останній задачі.
3. **Лише з окремого дозволу**: `cms:pull` → `cms:import` (dry-run: оновлення компонентів і `update`
   кожної історії з форматованими полями, без конфліктів) → `cms:import -- --apply` → повторний dry-run
   (`0 змін`) → `cms:verify`. `--force` не потрібен (див. «Модель і конвертація»). Злиття гілки може
   бути і до цього кроку: до імпорту `cms:pull` читає рядки старої моделі як документи.

## Ризики

| Ризик | Що робимо |
|---|---|
| Редактор Storyblok дописує атрибути, яких немає в allowlist | нормалізація у `fromStory`; тест на реальному документі з редактора (Задача з живим простором) |
| Зміна типу поля textarea → richtext на існуючих історіях | `fromStory` читає рядок як документ; імпорт без `--force` оновлює історії; повторний dry-run показує `0 змін` |
| Посилання на файл медіатеки Storyblok у тексті | `uploads/…` у `linkUrl`; тест `cms:pull` з таким посиланням |
| Блоковий текст зсуває вигляд детальних сторінок | скріншоти всіх сторінок до/після на поточному контенті, побайтове порівняння PNG |
| Посилання з richtext на неіснуючу сторінку | потрапляє в HTML → `findBrokenLinks` валить `npm test` |
| Битий якір (`#contacts` → id немає) | нова перевірка якорів у `site.test.js` |

## Критерії готовності

1. Усі поля з таблиці рівнів — richtext у Storyblok з обмеженою панеллю; прості поля не змінилися.
2. Схема відкидає все поза allowlist із зрозумілим повідомленням; `npm test` зелений.
3. На поточному контенті статичний вихід відрізняється від вихідного лише очікуваним (див. план),
   e2e-скріншоти збігаються.
4. Пробна збірка з повним форматуванням у кожному полі збирається, розмітка валідна, битих
   посилань немає.
5. Кожна кнопка з таблиць веде на адресу зі свого поля; порожні необовʼязкові — на фолбек.
6. Файли → Storyblok → файли — без різниці (`cms:verify` на фейку; на живому просторі — після імпорту).
7. CLAUDE.md описує richtext, рівні, `linkUrl` і `Rich.astro`.
