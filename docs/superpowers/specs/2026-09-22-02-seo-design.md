# Спека 2. SEO

**Дата:** 2026-09-22
**Порядок:** рішення про URL і локалі **читаються першими** як вхідні дані для Спеки 1.
Реалізація — **другою**, після того як сторінки й layout існують.

## Мета

Зробити сайт індексованим: обидві мови в пошуку, повний набір мета-тегів, структуровані
дані для локальної видачі, керовані URL.

## Поточний стан: SEO відсутнє

Аудит усіх 10 сторінок:

| Елемент | Стан |
|---|---|
| `<title>` | **0** — жодного заголовка на жодній сторінці |
| `<meta name="description">` | 0 |
| Open Graph / Twitter cards | 0 — при тому, що підключений Facebook SDK і посиланнями ділитимуться |
| `rel="canonical"` | 0 |
| JSON-LD | 0 |
| `sitemap.xml`, `robots.txt` | відсутні |

Єдині мета-теги — `charset` і `viewport`, продубльовані в `<head>` і в `<helmet>`.

Три структурні дефекти, які не лікуються додаванням тегів:

1. **URL деталок — query-параметри**: `ministry.dc.html?id=youth`, `church.dc.html?id=kryvyi-rih`.
2. **Англійська версія не існує як URL.** Перемикач мов підміняє `innerHTML` на тій самій
   адресі й запамʼятовує вибір у `localStorage` (`index.html:902`, `index.html:935`).
   Для пошукової системи англійської версії немає взагалі.
3. **Контент має лишитися в HTML.** Це визначає вибір статичної збірки у Спеці 1: якщо
   рендерити на клієнті, текст зникне з вихідного HTML і жодні подальші налаштування
   цього не виправлять.

### Чому це не можна відкласти «на після контенту»

Контентна частина SEO (тексти `title` і `description`, `alt`, заміна заглушок) справді
робиться після актуалізації контенту. Але архітектурна частина — структура URL, схема
локалей, режим рендерингу — це те саме рішення, що й вибір стека. Змінити URL після
індексації означає редіректи й втрату позицій.

**Пом'якшувальна обставина:** сайт ще ніде не задеплоєний і не проіндексований. Боргу
по редіректах немає, тому зараз структуру можна закласти правильно безкоштовно.

## Структура URL

Українська — основна, у корені. Англійська — під префіксом `/en/`.
Слаги **англійські й спільні для обох локалей**; відрізняє їх лише префікс.

| Сторінка | Зараз | uk | en |
|---|---|---|---|
| Головна | `index.html` | `/` | `/en/` |
| Служіння, список | `ministries.dc.html` | `/ministries/` | `/en/ministries/` |
| Служіння, деталь | `ministry.dc.html?id=youth` | `/ministries/youth/` | `/en/ministries/youth/` |
| Церкви обʼєднання | `churches.dc.html` | `/churches/` | `/en/churches/` |
| Церква, деталь | `church.dc.html?id=kryvyi-rih` | `/churches/kryvyi-rih/` | `/en/churches/kryvyi-rih/` |
| Проєкти | `projects.dc.html` | `/projects/` | `/en/projects/` |
| Проєкт, деталь | `project.dc.html?id=…` | `/projects/<slug>/` | `/en/projects/<slug>/` |
| Свідчення | `testimonies.dc.html` | `/testimonies/` | `/en/testimonies/` |
| Пастори | `pastors.dc.html` | `/pastors/` | `/en/pastors/` |
| Лідерам | `leaders.dc.html` | `/leaders/` | `/en/leaders/` |
| Про церкву | — | `/about/` | `/en/about/` |
| Контакти | — | `/contacts/` | `/en/contacts/` |
| Пожертви | — | `/donate/` | `/en/donate/` |

Наявні `id` у даних (`bible-school`, `home-groups`, `youth`, `kryvyi-rih`) вже англійські —
стають слагами **без змін**, міграція в цій частині безкоштовна.

Слаг — окреме поле в даних, а не похідне від заголовка: інакше редактор, виправивши назву,
мовчки зламає адресу.

Конвенція: **з кінцевим слешем**, канонічний хост — **без `www`**, з редіректом `www → без www`.

## Локалі та hreflang

На кожній сторінці:

```html
<link rel="canonical"  href="https://<домен>/ministries/youth/">
<link rel="alternate" hreflang="uk"        href="https://<домен>/ministries/youth/">
<link rel="alternate" hreflang="en"        href="https://<домен>/en/ministries/youth/">
<link rel="alternate" hreflang="x-default" href="https://<домен>/ministries/youth/">
```

- `x-default` веде на українську — основна аудиторія в Кривому Розі.
- `hreflang` мають бути **взаємними**: якщо uk вказує на en, en мусить вказувати назад,
  інакше Google ігнорує звʼязок.

### Перемикач мов

Найважливіша поведінкова зміна:

- перемикач стає звичайним `<a href>` на URL-відповідник тієї ж сторінки;
- **автоматичне перенаправлення за збереженою мовою прибирається повністю.** Воно
  найнебезпечніше для індексації: робот може отримати не той контент, що за адресою,
  і англійські сторінки не потраплять в індекс;
- логіка захоплення української з DOM (`index.html:899`) зникає — обидві мови приходять
  з даних як рівноправні.

## Мета-теги та ланцюжок фолбеків

Кожна сторінка й кожен запис колекції має групу SEO-полів:

| Поле | Якщо не заповнено |
|---|---|
| `metaTitle` (uk/en) | береться `name` / `title` |
| `metaDescription` (uk/en) | береться `summary` / `lead`, обрізане |
| `ogImage` | перше зображення з `media[]`, далі `defaultOgImage` з `site-settings` |
| `noindex` | вимкнено |

Ланцюжок фолбеків принциповий: редактор додасть служіння й не заповнить SEO — сторінка
все одно вийде з валідним заголовком і карткою для соцмереж.

Мінімальний набір на кожній сторінці:

```html
<title>…</title>
<meta name="description" content="…">
<meta property="og:title" content="…">
<meta property="og:description" content="…">
<meta property="og:image" content="…">
<meta property="og:type" content="website">
<meta property="og:locale" content="uk_UA">
```

`og:image` критичний окремо: підключений Facebook SDK, посиланнями ділитимуться, а зараз
при поширенні не підтягується ні заголовок, ні картинка.

## Три нові сторінки

`/about/`, `/contacts/`, `/donate/` — секції головної, що заслуговують власних URL
за окремими пошуковими намірами.

**Спосіб реалізації — обраний варіант «лише футер»:**

- головна **не змінюється візуально зовсім**: ні кнопок, ні нових блоків;
- єдиний шлях до нових сторінок — посилання у блоці навігації футера;
- для сканування й індексації цього достатньо: роботу потрібен лише шлях за посиланням.

**Компроміс, прийнятий свідомо:** живий відвідувач майже не знайде ці сторінки, і без
внутрішніх посилань із тіла сторінок вони накопичують менше ваги. Сторінки працюють
на пошук, не на навігацію.

### Обовʼязкова умова

**Окремий URL не ранжуватиметься, якщо на ньому той самий текст, що на головній.**
Google побачить дубль і залишить щось одне. Тому кожна з трьох сторінок потребує
**власного розгорнутого тексту двома мовами**.

Наслідок для планування: **сторінки вмикаються по одній, у міру готовності тексту.**
Краще дві сторінки з нормальним текстом, ніж три заглушки в індексі.

Щоб уникнути розсинхрону фактів, адреса, телефон і час служінь на `/contacts/` беруться
з `contact-info` (див. Спеку 1), а не дублюються текстом.

### Що не отримує окремої сторінки

`#media` — стрічка Facebook, власного унікального змісту немає.
`#ministries`, `#pastors`, `#union` — вже ведуть на `/ministries/`, `/pastors/`, `/churches/`.

## Розподіл цільових запитів

Одна сторінка — один основний намір, щоб сторінки не конкурували між собою:

| Сторінка | Основний намір |
|---|---|
| `/` | бренд + «церква Кривий Ріг» |
| `/about/` | «про церкву», «у що вірять» |
| `/contacts/` | «адреса церкви Кривий Ріг», «час богослужіння» |
| `/donate/` | «пожертвувати церкві», «підтримати служіння» |
| `/ministries/<slug>/` | назва конкретного служіння |
| `/churches/<slug>/` | назва церкви + місто |

## Структуровані дані (JSON-LD)

Генеруються з полів, які вже є в даних:

- **`Church`** на `/` і на сторінці кожної церкви: назва, адреса, місто, `geo` (lat/lng),
  `openingHours` (час богослужінь), телефон, `sameAs` (соцмережі);
- **`Organization`** з логотипом;
- **`BreadcrumbList`** на всіх вкладених сторінках.

Для церкви це найцінніше SEO на вкладену гривню — саме воно відповідає за картку
в локальній видачі з адресою й часом служінь. Координати `geo.lat` / `geo.lng` — нові
поля, яких зараз немає ніде (див. `contact-info` у Спеці 1).

## Технічні файли

### `sitemap.xml`

Генерується автоматично, включає обидві локалі з перехресними `hreflang`.

### `robots.txt`

Посилання на `sitemap.xml`, без блокувань. Прев'ю-стенд (Спека 3) — навпаки, закритий
від індексації повністю.

### `.htaccess` (Apache / OpenLiteSpeed на ukraine.com.ua)

- редірект `http → https`;
- редірект `www → без www` (канонічний хост — без `www`);
- чисті URL: `/ministries/youth/` без `.html`;
- нормалізація кінцевого слеша;
- **301 зі старих адрес** `*.dc.html?id=…` — пріоритет низький, бо сайт не проіндексований,
  але дешево і рятує, якщо хтось уже десь поділився посиланням;
- заголовки кешування для шрифтів, CSS і зображень;
- gzip / brotli — без цього статика на shared-хостингу віддається помітно повільніше.

## Що робиться пізніше, під час актуалізації контенту

Це та частина, яку замовник і планував робити після контенту:

- тексти `title` і `description` під кожну сторінку, двома мовами;
- `alt` до всіх зображень;
- заміна 31 заглушки `picsum.photos` на реальні фото;
- розгорнуті тексти для `/about/`, `/contacts/`, `/donate/`;
- підключення Search Console, перевірка індексації **обох** мов, доналаштування
  за реальними запитами.

## Ризики

| Ризик | Мітигація |
|---|---|
| Три нові сторінки лишаться порожніми в індексі | не вмикати, поки немає унікального тексту |
| `hreflang` не взаємні → Google ігнорує звʼязок | генерувати обидва боки з одного конфігу, перевірити після деплою |
| Автоперехід за `localStorage` випадково лишиться | явний пункт перевірки; це блокер індексації en |
| Слаг згенерований із заголовка → ламається при правці назви | слаг — окреме поле в даних |

- [x] `canonical` і взаємні `hreflang` (uk / en / x-default) на кожній сторінці
- [ ] OG-теги проставляються, картка коректно розгортається при поширенні у Facebook — теги/правила є; перевірка на домені: [чекліст](../notes/2026-09-23-seo-launch-checklist.md)
