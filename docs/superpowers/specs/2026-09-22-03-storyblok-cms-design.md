# Спека 3. Storyblok як CMS

**Дата:** 2026-09-22
**Порядок:** реалізується **третьою**, після Спек 1 і 2. Потребує готової схеми даних
зі Спеки 1 і працюючого задеплоєного сайту.

## Мета

Дати одному нетехнічному редактору можливість редагувати весь контент сайту — тексти,
колекції, фото, обидві мови — через візуальний інтерфейс, без доступу до коду.

## Рішення і чому саме воно

| Варіант | Чому не | |
|---|---|---|
| Кастомна адмінка | обсяг (колекції + тексти головної + медіатека + дві мови) — це повноцінна CMS: авторизація, завантаження й стиснення зображень, парні uk/en поля, валідація, прев'ю, ревізії. Найгірший ROI | ✗ |
| Payload | потребує постійно працюючого Node-сервера й БД. Заявлений хостинг — shared без Node. Щомісячний рахунок + обовʼязок роками оновлювати застосунок | ✗ |
| git-based (Keystatic / Sveltia) | $0 назавжди й контент у своєму репо, але редактору потрібен GitHub-акаунт | запасний |
| Sanity | 20 місць, вхід гуглом, CDN на 100 ГБ, але на free-тарифі **всі редактори — адміністратори** | запасний |
| **Storyblok** | **візуальне редагування: редактор клікає по тексту на справжній сторінці** | **✓** |

Вирішальним став профіль користувача: **один нетехнічний редактор**. За цієї умови
обмеження безкоштовного тарифу Storyblok не спрацьовують, а візуальний редактор дає
найменший поріг входу з усіх варіантів.

## Ліміти безкоштовного тарифу Starter

| Ліміт | Потреба проєкту | |
|---|---|---|
| 1 місце (макс. 2) | 1 редактор | ✓ є запас на другого |
| Visual Editor | головна причина вибору | ✓ включений на Starter |
| **2 локалі** | uk + en = рівно 2 | ⚠ впритул, запасу немає |
| 2 000 файлів | ~300–600 зображень у галереях | ✓ |
| 100 ГБ трафіку / міс | сайт церкви | ✓ |
| 100 000 API-запитів / міс | див. нижче | ✓ величезний запас |

### Чому ліміт API не спрацьовує

Наслідок статичної збірки зі Спеки 1: **запити до Storyblok робляться на білді,
а не відвідувачами.** Одна збірка — десятки запитів; навіть сто публікацій на місяць
дають кілька тисяч, тобто одиниці відсотків ліміту.

Якби контент тягнувся в рантаймі, ці 100 000 зʼїдав би трафік і ліміт став би реальним.

### Стелі, відомі наперед

1. **Рівно 2 локалі.** Третя мова = перехід на Growth ($99/міс) + $20 за локаль.
   **Замовник підтвердив, що третя мова не планується**, тож ця стеля не тисне —
   uk + en займають ліміт рівно і назавжди.
2. **Стеля у 2 редактори.** Третій редактор = $99/міс. Це єдине обмеження, яке реально
   може спрацювати з часом: редактор зараз один, але склад команди церкви змінюється.

Планування публікацій за розкладом і вбудований SEO-плагін — платні функції. Друге
нас не стосується: мета-теги генерує Astro зі звичайних текстових полів (Спека 2).

### Ризик вендора обмежений архітектурою

Через статичну збірку **Storyblok не є частиною працюючого сайту**. Якщо сервіс ляже,
змінить ціни чи акаунт загубиться — сайт продовжить працювати на останній зібраній версії
разом з усіма зображеннями. Зупиниться лише редагування.

### План відходу

Умова переходу, зафіксована наперед: **потреба в третьому редакторі.**
(Третю мову замовник виключив, тож ліміт локалей спрацювати не має.)
Оскільки схема даних визначена у Спеці 1 і не залежить від Storyblok, заміна джерела —
це дні, а не тижні. Цільові варіанти: Keystatic ($0, контент у репо) або Sanity
(20 місць, вхід гуглом).

## Відображення схеми на Storyblok

> **Уточнено 2026-09-24 (перед Етапом 4).** Початкова таблиця писалася до Етапів 1–3; модель
> відтоді змінилася (9 сторінок у `pages.json`, вкладені групи головної, необовʼязкова SEO-група).
> Нижче — актуальне відображення, погоджене перед реалізацією. Джерело правди моделі —
> zod-схема (`content.config.ts`), модель Storyblok їй **підпорядкована** і звіряється тестом.

### Простір

- Простір «Dim Hliba», регіон **EU** (`mapi.storyblok.com`). Створено 2026-09-24 на пробному
  тарифі (до 2026-11-08); після нього простір лишається на безкоштовному Starter. Модель
  тримається в межах Starter: жодної функції платних тарифів.
- **Мовний механізм Storyblok не використовується.** Пари `{uk, en}` — це два поля поруч
  (`name_uk`, `name_en`), обидва обовʼязкові. Причина: у вбудованому перекладі на рівні полів
  неперекладене поле API мовчки віддає українським текстом — англійська сторінка показала б
  українську, а збірка не змогла б цього помітити. Це ламає правило проєкту «відсутній переклад
  валить збірку». Парні поля ж відображаються на схему 1:1, а порожній переклад видно у формі.
  Обидві локалі Starter лишаються вільними.

### Структура (70 історій)

| Файли | Storyblok |
|---|---|
| `ministries`, `churches`, `projects`, `testimonies`, `pastors`, `leader-resources` (57 записів) | 6 папок, історія на запис; папка обмежена своїми типами контенту |
| `pages.json` (9 записів: about, contacts, donate, churches, ministries, projects, testimonies, pastors, leaders) | папка `pages/`, історія на сторінку, slug історії = id сторінки |
| `homepage`, `site-settings`, `contact-info`, `donate-settings` | 4 історії в папці `settings/` |

Демо-вміст нового простору (компоненти `page`, `teaser`, `grid`, `feature`, історія `home`)
прибирається першим імпортом.

### Правила відображення

| Схема (zod) | Storyblok |
|---|---|
| `{uk, en}` (`localized`, `localizedHtml`) | два поля `<ключ>_uk` / `<ключ>_en`, підписи «… (укр.)» / «… (англ.)»; `textarea` для довгих текстів, інакше `text` |
| `localized.optional()` | обидва поля порожні = ключа немає |
| `localized.nullable()` | обидва поля порожні = `null` |
| `slug` запису колекції | **slug історії** (не окреме поле): він і є адресою в папці, унікальність у папці гарантує Storyblok |
| `order` | числове поле «Порядок» (діри й дублікати дозволені, як у файлах) |
| число (`order`, `percent`, `defaultAmount`, `geo.*`, …) | поле `number`; Storyblok зберігає число **рядком** — конвертер перетворює в обидва боки |
| `boolean` (`seo.noindex`) | поле `boolean`; відсутнє = `false` |
| `enum` (18 іконок служінь, іконки ресурсів, формати, групи пасторів) | поле-список з фіксованими значеннями; значення беруться з `src/lib/icons.mjs` і схеми, а не пишуться вдруге |
| вкладена група (`hero`, `about`, `seo`, `progress`, `geo`, `help`, `sections`, …) | вкладений блок, максимум 1 (для обовʼязкових груп — рівно 1). Так «групи немає» відрізняється від «група є» |
| масив (`media`, `beliefs`, `news.items`, `stats`, `calcIncrements`, …) | список блоків |
| союз `testimonies` за `type` | два типи контенту: `testimony_text` / `testimony_video`, кожен зі своїми обовʼязковими полями |
| `leader-resources` за `kind` | два типи контенту: `resource_document` (формат, без іконки) / `resource_link` (іконка, без формату) |
| `mediaItem` за `type` | два блоки галереї: `gallery_image` (картинка з медіатеки) / `gallery_video` (посилання YouTube) |
| картинка (`src`, `photo`, `poster`, `logo.*`, `heroImage.*`, `ogImage`, `defaultOgImage`, `news.items[].image.src`) | поле `asset` (картинки) з дозволеною зовнішньою адресою |
| `leader-resources.url` | текстове поле URL і для документа, і для посилання. **Уточнено 2026-09-24:** замовник додає файли посиланнями на хмару (Google Диск тощо), тож документ має поля «Назва» + «Посилання на файл», а не файл у медіатеці |

- **Картинки.** 4 файли, на які посилається контент (`uploads/hero-cross.jpg`,
  `uploads/hero-cross-mobile.jpg`, `uploads/logo.png`, `uploads/logo-en.png`), завантажуються
  в медіатеку. 95 заглушок `picsum.photos` / `images.unsplash.com` лишаються **зовнішніми
  посиланнями**: їх однаково замінять реальними фото (дірка 5), а в медіатеці вони були б сміттям.
  `public/uploads/draw-*.png` контент не використовує — не переносяться.
- **Не переносяться** поля, яких шаблони не читають: `homepage.pastors.role` / `role2` (дірка 18).
  Вони прибираються з даних і зі схеми **до** імпорту — тоді файли й Storyblok збігаються повністю,
  а тест відповідності не потребує жодного винятку.
- **Для редактора:** українські підписи полів, вкладки «Контент» / «Галерея» / «SEO» / «Службове»,
  `required` на обовʼязкових полях. `required` Storyblok перевіряє лише у формі редактора (не в
  API) — справжня сітка безпеки лишається на збірці.

## Міграція даних (Етап 4)

### Модулі

| Модуль | Роль |
|---|---|
| `src/lib/schema.mjs` | zod-схеми, винесені з `content.config.ts` без змін у правилах (`z` з `astro/zod`); `content.config.ts` лише підключає їх до завантажувачів. Так схему бачать і Astro, і скрипти, і тести |
| `src/lib/storyblok/model.mjs` | декларативна модель: компоненти, поля, типи, підписи, вкладки, `required`, папки |
| `src/lib/storyblok/convert.mjs` | чисті `toStory(collection, data)` / `fromStory(collection, story)`. На Етапі 5 `fromStory` без змін стає завантажувачем Astro |
| `src/lib/storyblok/components.mjs` | генерує JSON компонентів Storyblok з моделі |
| `scripts/cms/` | клієнт Management API (≤ 3 запити/с, повтор на 429 з експоненційною паузою), `import.mjs`, `verify.mjs` |

Токен і id простору — лише в `.env` (у `.gitignore`): `STORYBLOK_MANAGEMENT_TOKEN`,
`STORYBLOK_SPACE_ID`, `STORYBLOK_REGION`. Скрипти читають його через `node --env-file`.

### Імпорт — `npm run cms:import`

1. **Валідація спершу.** Контент проганяється через ті самі zod-схеми, що й збірка. Невалідні
   дані не доходять до Storyblok узагалі — API обовʼязковості полів не перевіряє.
2. **Типово — сухий прогін:** план «створити / оновити / видалити» по компонентах, папках,
   історіях і файлах медіатеки. Змінює простір лише `--apply`.
3. **Ідемпотентно:** компоненти — за імʼям, історії — за повним slug (`ministries/youth`), файли
   медіатеки — за іменем і SHA-256 вмісту (той самий файл удруге не завантажується). Повторний
   прогін без змін у файлах — «0 змін».
4. Кожна історія **публікується** — Етап 5 читатиме опубліковану версію.
5. **Зайві історії** (є в наших папках Storyblok, немає у файлах) — лише попередження; видаляються
   тільки з `--prune`. Демо-вміст простору — окремий рядок плану, прибирається першим `--apply`.
6. **Запобіжник від перезапису правок редактора.** Кожна записана історія несе відбиток
   (SHA-256 канонічного JSON даних) у службовому полі. Перед оновленням імпорт перераховує відбиток
   того, що зараз у Storyblok: якщо він не збігається із записаним, історію хтось змінював — імпорт
   відмовляється її перезаписувати без `--force`. Після Етапу 5 джерелом правди стає Storyblok, і
   саме це не дасть випадковому імпорту з файлів стерти роботу редактора.

### Звірка — `npm run cms:verify`

Читає всі історії, проганяє через `fromStory` і порівнює з файлами поле за полем. Картинки з
медіатеки завантажує й звіряє за SHA-256 з файлом у `public/`. Розбіжність — конкретним рядком
(«`ministries/youth` → `summary.en`: очікувалось …, у Storyblok …») і ненульовим кодом виходу.

**Критерій приймання Етапу 4:** `cms:verify` на живому просторі — нуль розбіжностей.

«Побайтово» означає рівність **даних**, а не URL: адреса картинки з медіатеки після
завантаження інша, тож рівність — за вмістом файлу. Одне свідоме уточнення: у `pages.*.body` схема
дозволяє і відсутність ключа, і `null`, а Storyblok їх не розрізняє — для цього поля «немає»
≡ `null` (шаблони трактують обидва однаково, `isPageEnabled`).

### Тести (`npm test`, без мережі й токена)

- **Відповідність моделі схемі:** обхід zod-схеми — модель покриває рівно ті самі ключі з
  сумісними типами, без винятків. Службове поле відбитка — поза схемою даних і поза `fromStory`. Нове поле в схемі без поля в моделі — червоний тест.
- **Туди й назад:** `fromStory(toStory(x))` дорівнює `x` для кожного реального запису й для
  пробних наборів з усіма необовʼязковими полями, `null` і порожніми списками.
- **Фейковий Management API:** HTTP-сервер у памʼяті з тими самими ендпоінтами, лімітом і 429.
  На ньому: повний імпорт → `verify` зелений; повторний імпорт → 0 змін; ручна зміна історії →
  відмова без `--force`; `--prune`; невалідні дані → жодного запиту на запис.
- Живий простір у CI не залучається.

## Інтеграція з Astro

Джерело даних міняється з локальних файлів на Storyblok; **схема лишається та сама**,
тому сторінки й компоненти не переписуються.

### Зображення

Завантажуються з Storyblok **на етапі збірки** і кладуться поруч із сайтом, а не
віддаються з їхнього CDN.

Навіщо:

- сайт стає самодостатнім — жодного звернення до Storyblok із браузера відвідувача;
- Astro дорогою стискає й генерує потрібні розміри;
- 10 ГБ диска на хостингу вистачає з великим запасом;
- прибирається остання залежність: якщо Storyblok зникне, працюватимуть і сайт,
  і всі його зображення.

## Прев'ю-стенд і Visual Editor

Visual Editor вантажить сайт в iframe усередині адмінки. Для цього потрібні:

1. **HTTPS-адреса прев'ю** — адмінка на https, http-iframe блокується;
2. **Storyblok Bridge** на сторінці — підключати лише коли в URL є `?_storyblok`,
   щоб не вантажити його живим відвідувачам;
3. **атрибути `_editable`** на редагованих блоках — вони звʼязують DOM з полем;
4. **рендер із чернеткового API в момент запиту** — щоб редактор бачив незбережене.

### Де він живе

Продакшн-хостинг не підходить: Node на тарифі «Швидкий» не заявлений, а ліміт «1 сайт»
не дозволив би другий стенд.

**Рішення:** прев'ю-стенд на **Cloudflare Pages** (безкоштовно), у серверному режимі,
з draft-токеном. Продакшн лишається статичним на ukraine.com.ua.

Дві конфігурації збірки замість однієї — це ціна візуального редагування.

Прев'ю бачить лише редактор; стенд **закривається від індексації** (див. Спеку 2).

## Публікація

```
Редактор натискає «Опублікувати» в Storyblok
        │ вебхук
        ▼
GitHub Actions: astro build
        │  (схема невалідна → збірка падає,
        │   зламаний контент не доходить до сайту)
        ▼
rsync по SSH → ukraine.com.ua
        ▼
Сайт оновлено, ~1–2 хвилини
```

**Публікація одразу в ефір, без кроку підтвердження** — рішення прийняте свідомо:
редактор один і він бачить результат у Visual Editor під час редагування, тож окремий
крок узгодження лише заважав би.

Страхувальна сітка лишається на рівні збірки: невалідний контент не публікується.

## Передача редактору

- коротка інструкція **українською** — інтерфейс Storyblok англійський, тож це не
  формальність;
- показати наживо: де що редагується, як додати служіння, як залити фото, що станеться
  після «Опублікувати»;
- окремо проговорити, що `slug` змінювати не можна без потреби — це адреса сторінки.

**Готово коли:** людина самостійно вносить правку від початку до кінця, без допомоги.
